Chapter 1

Introduction

1.1 Project Overview

In modern healthcare facilities, managing patient appointments manually leads to prolonged waiting queues, scheduling errors, lost records, and patient frustration. Furthermore, patients often delay seeking medical attention due to a lack of early awareness regarding subtle symptoms.

The Smart Medical Appointment and Risk Prediction System is a computerized web application developed to bridge this gap. Built using Java 17 and Spring Boot 3, it provides automated conflict-free doctor appointment scheduling alongside an automated Rule-Based Risk Prediction Engine that triages patient symptoms to promote early health awareness and guide timely clinical consultations.

1.2 Purpose and Objectives

  • Digital Scheduling: Eliminate physical OPD queues through computerized time-slot allocation.
  • Double-Booking Prevention: Enforce transactional database locks and slot availability validation.
  • Symptom Triage: Provide an automated rule-based risk prediction engine categorizing health urgency into LOW, MEDIUM, or HIGH risk.
  • Triage-to-Consultation Integration: Automatically pre-fill doctor consultation reasons for patients with high or moderate risk scores.
  • Clinical Records: Provide doctors with patient clinical profiles (Blood Group, Medical History) and consultation notes/e-prescription documentation tools.
  • Operational Traceability: Provide administrators with real-time analytics, exportable CSV reports, security audit trails, and portable SQL database backups.

1.3 Project Category & Web Development Life Cycle (WDLC)

The project falls under the category of Enterprise Web-Based Applications. It was engineered following the Web Development Life Cycle (WDLC):

  1. Requirement Analysis: Understanding outpatient workflows, doctor availability patterns, and clinical symptom rules.
  2. Planning: Defining the technology stack (Spring Boot 3, MySQL/H2, Bootstrap 5) and timeline.
  3. Design: Creating architectural blueprints, UML diagrams, DFDs (Level 0, 1, 2), and normalized 3NF schemas.
  4. Development: Writing clean backend REST controllers, service components, repositories, and responsive front-end views.
  5. Testing: Verifying system behavior using JUnit 5, Mockito, and Postman API test suites.
  6. Deployment: Packaging into a runnable JAR using Maven and hosting with embedded Tomcat.
  7. Maintenance: Establishing automated audit logging, database backup exports, and modular services for future scalability.

1.4 Scope & Limitations of the Existing System

Drawbacks of Traditional / Manual Systems:

  • Long waiting times and crowded physical reception queues.
  • Manual paper records prone to loss, wear, and misplacement.
  • High risk of double-booking due to uncoordinated scheduling across multiple receptionists.
  • Complete absence of preliminary symptom risk awareness.
  • Time-consuming manual report compilation.

Scope of Proposed System:

  • Covers outpatient appointment booking, rescheduling, and cancellation.
  • Provides dedicated portals for Patients, Doctors, and Hospital Administrators.
  • Incorporates deterministic health risk assessment based on 10 symptom indicators.
  • Provides complete disaster recovery database backup capabilities.

4.3 Rule-Based Risk Prediction Engine Logic

The risk prediction engine executes deterministic clinical decision rules evaluating patient age and 10 symptom factors:

flowchart TD Start["Patient Input: Age + Selected Symptoms"] --> Q1{"Contains CHEST_PAIN or
BREATHLESSNESS?"} Q1 -- YES --> High1["HIGH RISK
Urgent ER Medical Care Required"] Q1 -- NO --> Q2{"Age > 50 AND Symptoms contain
HIGH_BP & HIGH_SUGAR?"} Q2 -- YES --> High2["HIGH RISK
Urgent Specialist Consultation"] Q2 -- NO --> Q3{"Symptom Count >= 3 OR
(PROLONGED_COUGH & FEVER)?"} Q3 -- YES --> Med["MEDIUM RISK
Schedule Doctor Consultation"] Q3 -- NO --> Low["LOW RISK
Routine Outpatient Care"]
Figure 4.1: Rule-Based Clinical Triage Decision Logic

Symptom Weights: Chest Pain (+4), Breathlessness (+4), High BP (+2), High Sugar (+2), Prolonged Cough (+2), Fever (+1), Fatigue (+1), Headache (+1), Dizziness (+1), Weight Loss (+1). Age additions: Age ≥ 60 (+2), Age 40-59 (+1). Total Score: 0-3 (LOW), 4-7 (MEDIUM), 8+ (HIGH).

4.4 Seamless Triage-to-Booking Integration Flow

When an evaluated patient receives a HIGH or MEDIUM risk score:

  1. The results banner renders an urgent recommendation with a direct "Book Doctor Visit" action button.
  2. Clicking the action constructs a URL appending the triage context: ?reason=Risk+Assessment:+HIGH+Risk+-+Symptoms:...&fromRisk=true.
  3. The appointment booking view automatically intercepts query parameters, pre-populates the consultation reason, selects the appropriate specialty, and displays an informational referral banner.
  4. The consulting doctor sees the patient's reported symptoms, risk category, blood group, and medical history upon arrival.

4.5 Security Architecture & Stateless JWT Lifecycle

  • Stateless Authentication: Credentials submitted to POST /api/auth/login are verified via BCrypt. Upon successful verification, a signed JWT bearer token containing user ID, role, and username is issued.
  • Request Interception: JwtAuthenticationFilter intercepts incoming HTTP requests, extracts the Authorization: Bearer <token> header, verifies cryptographic validity, and injects user claims into Spring's SecurityContextHolder.
  • Role-Based Access Control (RBAC): REST endpoints are guarded with method-level authorization (@PreAuthorize("hasRole('ADMIN')"), @PreAuthorize("hasRole('DOCTOR')"), @PreAuthorize("hasRole('PATIENT')")).

Chapter 8

IGNOU Viva Voce Preparation Guide

Q1: What is the core problem solved by your project?
Answer: It addresses the severe outpatient congestion in traditional healthcare facilities by eliminating physical waiting queues, preventing scheduling conflicts (double-booking) through atomic database transactions, and providing early health risk awareness through an automated symptom triage engine.
Q2: How does the system prevent two patients from booking the same doctor slot simultaneously?
Answer: In AppointmentService.java, the booking method is annotated with Spring's @Transactional. Before persisting an appointment, the system evaluates slot.getIsBooked(). If true, it immediately throws SlotUnavailableException (HTTP 409 Conflict). If false, it sets isBooked = true and saves the appointment within the same atomic database transaction.
Q3: How does the Risk Prediction Engine operate?
Answer: Implemented in RiskPredictionService.java, it applies deterministic clinical rules across patient age and 10 vital symptom indicators. Critical symptoms (Chest Pain, Breathlessness) or elderly comorbidity (age > 50 with hypertension and diabetes) immediately yield a HIGH RISK classification. Furthermore, patients with elevated risk receive a pre-filled booking link directly into the appointment module.
Q4: How is security implemented in the application?
Answer: Using Spring Security 6 with stateless JSON Web Tokens (JWT). Passwords are encrypted using BCrypt with salt rounds. Endpoints are protected with method-level authorization (@PreAuthorize("hasRole('ADMIN')"), @PreAuthorize("hasRole('DOCTOR')"), @PreAuthorize("hasRole('PATIENT')")).
Q5: How does the Database Backup and Security requirement from Module 9 work?
Answer: Implemented in DatabaseBackupService.java, an authenticated administrator can trigger GET /api/admin/database/backup to generate and download a complete, portable SQL dump of all system tables (admin, doctor, patient, doctor_slot, appointment, risk_report) with sanitized foreign key checks for disaster recovery and offline archiving.
